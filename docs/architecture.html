GL1TCH OS — architecture

How the pieces fit together, boot to shell prompt

Boot chain overview

GL1TCH OS boots in three stages off a 1.44 MB FAT12 floppy image, each stage loading and jumping to the next. This mirrors the classic "stage1 loads stage2 loads kernel" design used by most x86 real-mode hobby OSes, because the BIOS only ever loads the first 512 bytes of the boot device for you — everything after that, the OS has to load itself.

BIOS | loads sector 0 (512 bytes) to 0000:7C00, jumps to it v stage1 (src/bootloader/stage1/stage1.asm) | 512-byte boot sector; contains the FAT12 BPB + a tiny FAT reader | just capable enough to find and load STAGE2.BIN | loads it to 0000:0500, jumps there v stage2 (src/bootloader/stage2/*.asm, main.c) | real mode, grown-up FAT12 reader (reads boot drive geometry via | BIOS, walks the FAT chain) -- finds and loads KERNEL.BIN | loads it to 4000:0000, jumps there with the boot drive in dl v kernel (src/kernel/*.c, *.asm) | entry.asm sets up ds/es/ss/sp, calls kmain(boot_drive) | kmain initializes the FAT12 driver and starts the shell v shell (src/kernel/shell.c) interactive command loop, reads from the BIOS keyboard, writes to the BIOS teletype console, never returns

Why three stages instead of one

The BIOS hands control to exactly 512 bytes (one sector) with no filesystem awareness at all — stage1 is that sector, so it has to be both small enough to fit and just smart enough to read a FAT12 directory to find the next stage. Stage2 has a whole sector-aligned file to work with, so it can afford a sturdier FAT reader and, significantly, is the first stage built with a C compiler (Open Watcom) rather than hand-written assembly throughout. The kernel is loaded by stage2's FAT reader the same way stage2 itself was loaded by stage1's, which is why src/bootloader/stage2/x86.asm and src/kernel/fat.c solve a related problem (find a file by name, follow its cluster chain) twice, at two very different levels of capability.

Kernel module layout

The kernel is a single flat 16-bit real-mode binary (one 64 KB segment: code, data and stack all share it, ds == ss == cs), linked from these objects:

entry.asm ──calls──▶ kernel.c (kmain) │ ┌────────────┼────────────┐ ▼ ▼ ▼ x86.asm/.h console.c/.h fat.c/.h (BIOS calls) (output) (FAT12 driver) ▲ ▲ ▲ │ │ │ keyboard.c/.h │ kstring.c/.h (line input) │ (string/number helpers, │ │ used by everything above) └─────┬──────┴────────────┘ ▼ calc.c/.h ──┐ shell.c/.h ◀─┘ (command loop: help, ls, cd, pwd, cat, calc, echo, clear, reboot)

Why a strict layering, not everything calling everything

  • x86.asm is the only place that executes a BIOS interrupt or a raw I/O instruction. Every other module reaches hardware only through its cdecl function wrappers (x86_putc, x86_disk_io, …), so there is exactly one place to look when something at the BIOS boundary misbehaves. It also carries Open Watcom's 32-bit math runtime helpers (__U4M/__I4M/__U4D/__I4D), since the build links no default library and the compiler still emits calls to them for any uint32_t/int32_t multiply or divide.
  • kstring.c has no dependencies on anything else in the kernel — it's the leaf. Its functions are deliberately not named memcpy/strlen/strcmp/etc., because Open Watcom treats those specific names as compiler intrinsics and can silently emit a call using a different calling convention than the cdecl one actually defined here, corrupting arguments. Distinct names (mem_copy, str_len, …) sidestep that entirely.
  • console.c and keyboard.c depend only on x86.h: one turns characters/numbers into BIOS teletype calls, the other turns BIOS keystrokes into a NUL-terminated line (with backspace support).
  • fat.c depends on x86.h (for disk I/O) and kstring.h (for name comparison/formatting), but knows nothing about the shell. It owns all on-disk state: the parsed BPB, the cached FAT table, and the current-directory stack. It exposes a small visitor-style API (fat_list_cwd, fat_read_file each take a callback) so callers don't need to know about sectors, clusters or 32-byte directory entries at all.
  • calc.c depends on nothing but kstring.h. It's a pure string-in, integer-out expression evaluator with no awareness of the console or the shell, which is what makes it independently testable.
  • shell.c is the only module that depends on all the others. It is intentionally "dumb": it reads a line, splits it into words, and matches the first word against a fixed command table. All real behavior lives in the module that owns the relevant state (fat.c for ls/cd/ pwd/cat, calc.c for calc).

The FAT12 driver's internal model

fat.c treats "the root directory" and "a subdirectory" as the same abstraction wherever it can, because on FAT12 they are almost the same thing read two different ways:

  • The root directory lives at a fixed sector range computed from the boot sector's BPB (reserved_sectors + fat_count × sectors_per_fat), with a fixed number of 32-byte entries — it is not part of any cluster chain.
  • A subdirectory is stored exactly like a file: a cluster chain you follow through the FAT, whose "contents" happen to be more 32-byte directory entries instead of arbitrary bytes.

fat_iterate_dir(cluster, visitor, ctx) hides that difference behind one convention: cluster == 0 means "walk the fixed root sectors", anything else means "walk this cluster chain". Both paths funnel every sector through the same scan_sector entry parser, so there is one place that knows about deleted entries (0xE5), end-of-directory (0x00), long-filename fragments, and volume labels.

The current working directory is not read from on-disk ./ .. entries. It's a small stack the kernel keeps itself (cluster number + name per path segment, 8 levels deep), pushed on a successful cd into a subdirectory and popped on cd ... cd builds the new path on a temporary copy of that stack and only commits it if every segment resolves, so a cd a/b/nonexistent leaves the shell exactly where it started rather than partway into a/b.

Build pipeline

make (top-level) ├─▶ src/bootloader/stage1/makefile ──nasm──▶ build/stage1.bin ├─▶ src/bootloader/stage2/makefile ──nasm + wcc/wlink──▶ build/stage2.bin ├─▶ src/kernel/makefile ──nasm + wcc/wlink──▶ build/kernel.bin └─▶ tools/makefile ──gcc──▶ build/*.bin (host-side test files) │ ▼ dd + mkfs.fat + mcopy ──▶ build/main_floppy.img (1.44MB FAT12 floppy)

Stage2 and the kernel are both built with Open Watcom (wcc/ wlink), the only C compiler in this toolchain that still targets 16-bit real mode; stage1 is pure NASM; the tools/ directory is ordinary native (gcc) code that runs on the host, not inside the OS — it's separate from the boot chain. The Dockerfile wraps all of this in a reproducible Ubuntu 24.04 image so the exact toolchain versions don't have to be installed on the host; see the 2026-10-06 report for what had to be fixed to get that working.

Testing without a serial port

The kernel talks to the BIOS console (int 10h/int 16h), not a serial UART, so it can't be tested by just piping text at QEMU's -serial stdio. It was instead tested by booting QEMU headless with a monitor socket, sending real keystrokes with the monitor's sendkey command, and reading the result straight out of the VGA text buffer in guest memory (pmemsave 0xb8000 4000 ..., 80×25 cells × 2 bytes) — a deterministic, screenshot-free way to drive and verify a BIOS-console kernel.
