Docker build fix, and a C kernel shell with arithmetic + file explorer

2026-10-06 · Claude Opus 5.5 / Claude Sonnet 5, with Jihad Mimouni

Summary

The Docker build was broken (Open Watcom's "Current-build" release asset had been renamed, and the runtime image had a floppy-image permission/format problem) and both are now fixed. On top of that, the kernel's placeholder "Hello world" assembly stub was replaced with a small C kernel: a real interactive shell with a recursive-descent arithmetic evaluator (calc) and a read-only FAT12 file explorer with Linux-like commands (ls, cd, pwd, cat). It was built with the project's own Docker toolchain and verified by actually booting it in QEMU and driving the shell.

What happened

1. Docker build: Open Watcom download 404

docker build -t gl1tch-os . failed at the Open Watcom step with curl: (22) The requested URL returned error: 404. The Dockerfile hardcoded .../releases/download/Current-build/owsnapshot.tar.xz, and that asset name no longer matches what the release actually publishes.

Fix (Dockerfile): instead of hardcoding one filename, the build now asks the GitHub API for the Current-build release's assets and picks the first one matching *snapshot*.tar.xz, falling back to a guessed URL if that lookup comes back empty, and printing the URL it chose. A --build-arg WATCOM_SNAPSHOT_URL=... escape hatch is kept for pinning a specific file.

2. Docker run: permission denied and raw-format warning

After the image built, docker run --rm -it gl1tch-os failed with qemu-system-i386: Could not open '/os/main_floppy.img': Permission denied, plus a warning about QEMU guessing the image format. The floppy image was copied into the runtime stage owned by root, but the container runs as the unprivileged gl1tch user, and QEMU opens the floppy read-write.

Fix (Dockerfile): COPY --chown=gl1tch:gl1tch so the image file is owned by the user that runs it, and the entrypoint now passes -drive file=...,format=raw,if=floppy instead of the ambiguous -fda flag, which removes the format-guessing warning and its associated write restriction on block 0.

3. Kernel rewrite: from an asm stub to a C shell

The previous kernel (src/kernel/kernel.asm) only printed a hello-world string and halted. It was replaced with a small freestanding C kernel built with Open Watcom (matching the 16-bit toolchain already used for stage2), wired up with a new assembly entry point and BIOS glue:

  • entry.asm — real-mode entry point stage2 jumps to; sets up ds/es/ss and the stack, then calls kmain(boot_drive).
  • x86.asm / x86.h — cdecl BIOS wrappers (putc, clear_screen, getkey, reboot, disk reset/params/CHS read) plus the 32-bit math runtime helpers Open Watcom's 16-bit codegen calls into (__U4M/__I4M/__U4D/__I4D), which aren't provided since the build links no default library.
  • kstring.c / kstring.h — freestanding string/number helpers, deliberately not named memcpy/strlen/etc., since Open Watcom recognizes those names as compiler intrinsics and can emit calls with a different calling convention than the cdecl one used here.
  • console.c/.h, keyboard.c/.h — character output and line-buffered keyboard input (handles backspace).
  • calc.c/.h — the arithmetic evaluator: a recursive-descent parser for + - * /, parentheses, and unary minus, over 32-bit integers, with usual operator precedence and a division-by-zero check. This is exposed as the shell's calc command.
  • fat.c/.h — a FAT12 driver: reads the BPB from the boot sector at runtime (rather than hardcoding geometry), iterates the root directory and subdirectory cluster chains, resolves /-separated paths with ./.. and absolute-path support, and reads file contents. This backs the file explorer.
  • shell.c/.h — the interactive command loop: help, ls, cd <dir>, pwd, cat <file>, calc <expr>, echo <text>, clear/cls, reboot.
  • kernel.c — kmain: clears the screen, initializes the FAT driver on the boot drive, and hands off to the shell.
  • src/kernel/makefile — rewritten to compile the new *.c/*.asm sources with Open Watcom, mirroring stage2's existing build pattern.

4. Build and boot-test methodology

The whole project was built using the repo's own Docker toolchain image (no sudo needed — the system Docker socket at /var/run/docker.sock works directly), run as the invoking user's uid/gid so build output stays usable outside the container: 

docker run --rm -u "$(id -u):$(id -g)" -v "$(pwd)":/build -w /build gl1tch-toolchain \
  make BUILD_DIR=/build/build

The resulting build/main_floppy.img was booted headless in QEMU with a monitor socket, then the shell was driven by sending real keystrokes through QEMU's sendkey monitor command and reading the VGA text buffer directly out of guest memory with pmemsave 0xb8000 4000 ... (80x25 text mode, 2 bytes per cell) — a deterministic way to test a BIOS-console kernel without a serial port, with no OCR or screenshots involved.

How it was verified

After one bug fix (below), the full command set was exercised in a live QEMU boot and produced exactly the expected output: 

GL1TCH:/> calc 2+3*4
14
GL1TCH:/> calc 7-2
5
GL1TCH:/> calc 6/2
3
GL1TCH:/> calc 10/0
calc: division by zero
GL1TCH:/> ls
        STAGE2.BIN   8622 bytes
        KERNEL.BIN   9095 bytes
        FAT          15960 bytes
        HELLO.TXT    64 bytes
GL1TCH:/> pwd
/
GL1TCH:/> cat hello.txt
Hello from GL1TCH OS file explorer!
This is a test text file.
GL1TCH:/> cd nope
cd: no such directory
GL1TCH:/> cat missing.txt
cat: no such file or directory
GL1TCH:/> echo testing 123
testing 123

bug found & fixed calc and echo initially printed a "usage" error for every input. Cause: the shell's tokenizer splits the input line into arguments by overwriting each space with a NUL in place, but calc/ echo need the original free-form remainder of the line (an expression or text that may itself contain spaces), and that remainder was being read from the already-tokenized (and thus truncated-at-the-first-space) buffer. Fixed in shell.c by snapshotting the raw line into a second buffer before tokenizing, and reading the free-form remainder from that untouched copy.

Operator precedence (2+3*4 → 14, not 20), division-by-zero detection, directory/file error messages, and the FAT12 directory listing (correct names and byte sizes for every file actually on the built floppy) were all confirmed against real BIOS/QEMU behavior, not just read from the source.

Known limitations / follow-ups

  • The file explorer was read-only at the time of this report: no mkdir, touch, rm, or write support. (Since fixed — see the fat reference page for fat_mkdir/fat_create_file/fat_write_file/ fat_remove.)
  • cat prints raw file bytes with \n normalized to \r\n; it's meant for text files, not binaries.
  • fat_find_file doesn't support .. inside a file path (only cd does); it reports a clear error instead of silently misresolving.
  • The FAT12 driver reads the BPB at runtime rather than hardcoding geometry, but still assumes 512-byte sectors and caches at most 9 FAT sectors, matching this project's fixed mkfs.fat -F12 1.44 MB floppy layout — it isn't a general-purpose FAT12 implementation.
  • calc works in 32-bit signed integers only (no floating point, no overflow detection).
